== Cross-cutting Concepts

=== Modelo de Dominio

El sistema sigue un modelo de dominio centrado en la separación de responsabilidades:

* **Usuarios:** gestión de cuentas, autenticación y autorización (Auth Service + Users Service).
* **Partidas:** lógica de reglas, estado YEN, bots y validación de movimientos (Gamey Engine).
* **Salas multijugador:** emparejamiento, sincronización en tiempo real y chat (WS-Server).
* **Interacción Web:** comunicación entre frontend y backend mediante HTTP REST y WebSocket.
* **Monitorización:** recogida y visualización de métricas del sistema (Prometheus + Grafana).

=== Autenticación y Autorización — JWT

El sistema usa **JSON Web Tokens (JWT)** para autenticación stateless.

Flujo::
1. El cliente envía credenciales a `POST /auth/login` (ruta pública, sin token).
2. El Auth Service verifica contra Users Service y firma un JWT con `{ userId, username }` usando `JWT_SECRET`.
3. El cliente incluye el token en todas las peticiones posteriores: `Authorization: Bearer <token>`.
4. El Gateway valida el token en su `JwtFilter` (verificación local, sin roundtrip a BD) y añade `X-User-Id` al request.
5. Las rutas `/auth/*`, `/status` y `/actuator/health` son públicas y no requieren token.

Ventajas del enfoque::
- **Stateless**: el gateway no necesita consultar la BD para validar cada petición.
- **Desacoplado**: el Auth Service puede evolucionar (añadir OAuth, MFA) sin cambiar el gateway.
- **Seguridad**: el token expira (por defecto 1h); si se compromete, la ventana de ataque es limitada.

=== Notación YEN

El estado de todas las partidas se representa mediante la notación YEN (formato JSON):

[source,json]
----
{
  "size":    5,
  "turn":    0,
  "players": ["B", "R"],
  "layout":  "./../.../..../....."
}
----

* `layout`: filas separadas por `/`, cada carácter es `.` (vacío), `B` (Azul) o `R` (Rojo).
* `turn`: índice del jugador cuyo turno es (0 o 1).
* `players`: identificadores de los jugadores en orden.

=== Comunicación en Tiempo Real — WebSocket de Salas

El módulo `ws-server` implementa un protocolo de salas propio sobre WebSocket puro.

**Principio de diseño clave**: el servidor WS **no contiene lógica de juego**.
Solo empareja jugadores y retransmite mensajes. La validación de movimientos siempre
la realiza la API Rust (`/v1/game/play`). Esto garantiza que la lógica del juego
sea la misma para todos los modos (bot y multijugador).

Protocolo de mensajes::

[cols="1,1,2", options="header"]
|===
| Tipo | Dirección | Descripción
| `create` | Cliente → Servidor | Crea sala nueva. Recibe `roomCode` de 6 chars.
| `join` | Cliente → Servidor | Se une a sala existente por `roomCode`.
| `room_created` | Servidor → Cliente | Confirmación de sala creada con `roomCode`.
| `game_start` | Servidor → Ambos | La sala está llena. Incluye `playerIndex` asignado aleatoriamente.
| `board_update` | Cliente → Servidor → Oponente | Nuevo estado del tablero tras un movimiento.
| `game_over` | Cliente → Servidor → Oponente | Partida terminada con el ganador.
| `chat` | Cliente → Servidor → Oponente | Mensaje de texto. El servidor añade el campo `from`.
| `error` | Servidor → Cliente | Error de sala, conexión perdida o desconexión del oponente.
|===

Asignación aleatoria de color::
Cuando el segundo jugador se une a la sala, el servidor asigna los índices (0=Azul, 1=Rojo)
aleatoriamente mediante `Math.random() < 0.5`. Esto garantiza equidad en partidas entre humanos.

=== Geometría del Tablero Hexagonal

El tablero usa hexágonos **flat-top** (lados planos arriba/abajo, vértices a izquierda y derecha)
en forma de pirámide centrada: la fila 0 tiene 1 celda arriba y la fila n-1 tiene n celdas abajo.

La fórmula de centrado por fila:

[source]
----
offsetX(row) = (n - 1 - row) × (√3 · r) / 2
cx(row, col) = offsetX(row) + col × √3 · r
cy(row)      = row × 1.5 · r
----

La función `buildHexGeometry` y `flatHexPoints` se exportan desde `HexBoard.tsx` y son
reutilizadas por `GameHistory.tsx` (miniaturas del historial), garantizando que ambas
representaciones son geométricamente idénticas.

=== API de Competición — `GET /play`

El endpoint `GET /play` permite a bots externos consultar qué jugada elegiría el bot de la aplicación dado un estado de tablero en formato YEN. El cliente envía el estado actual como query parameter y recibe las coordenadas elegidas por el bot.

Internamente realiza una sola llamada a Gamey Engine:

1. `POST /v1/ybot/choose/{bot_id}` → el bot elige su jugada y devuelve `{ coords }`.

Parámetros:

* `position` (obligatorio): estado del tablero en formato YEN serializado como JSON string.
* `bot_id` (opcional, por defecto `random_bot`): identificador del bot a usar.

Bots disponibles: `random_bot` (aleatorio), `greedy_bot` (codicioso), `minimax_bot` (minimax profundidad 2).

=== Monitorización — Prometheus y Grafana

El Users Service expone métricas compatibles con Prometheus. La pila de monitorización funciona así:

* **Prometheus** hace scraping del endpoint de métricas del Users Service periódicamente y almacena las series temporales.
* **Grafana** se conecta a Prometheus como datasource y visualiza los datos en dashboards preconfigurados.
* Ambos servicios están incluidos en el `docker-compose.yml` y se levantan automáticamente.

Puertos de acceso::
- Prometheus: `http://localhost:9090`
- Grafana: `http://localhost:9091`

=== Experiencia de Usuario al Finalizar Partida

Al terminar una partida vs bot, el tablero permanece visible con el resultado.
El guardado en la base de datos se realiza **en background** (sin `await` bloqueante),
de forma que la UI responde inmediatamente. El jugador ve dos botones:

* **"Jugar de nuevo"**: reinicia el tablero con la misma configuración (mismo tamaño, dificultad y quién empieza) sin volver al menú.
* **"Volver al menú"**: navega al `GameModeSelector` para elegir nueva configuración o modo.

=== Experiencia de Usuario (UX)

- La interfaz sigue el patrón SPA para ofrecer fluidez y rapidez.
- Selección de modo de juego previa a la partida: modo (bot/multijugador), tamaño del tablero (mínimo 5), dificultad del bot y elección de quién empieza.
- En modo multijugador: pantalla de lobby con pestañas "Crear sala" / "Unirse a sala", con código de 6 caracteres y chat disponible durante la partida.
- Leaderboard global paginado accesible desde la NavBar.
- Perfil de usuario con estadísticas detalladas: tasa de victorias, racha, bots derrotados, top día y fecha de registro.
- Mensajes de error y estado consistentes en toda la aplicación.

=== Seguridad y Autenticación

- **JWT**: tokens firmados con `JWT_SECRET` compartido entre auth-service y gateway. Expiración configurable (por defecto 1h).
- **bcrypt**: contraseñas hasheadas con 10 salt rounds en Users Service. Nunca se almacenan en texto plano.
- **Nginx como punto de entrada único**: los puertos internos no están expuestos al exterior.
- **Rutas públicas mínimas**: solo `/auth/*`, `/status` y `/actuator/health` son accesibles sin token.
- El servidor WebSocket no requiere autenticación formal (partidas por código de sala).

=== Patrones de Arquitectura y Diseño

- **Microservicios**: cada servicio tiene una responsabilidad clara y se despliega en un contenedor Docker independiente.
- **Proxy inverso (Nginx)**: punto de entrada único para HTTP y WebSocket.
- **Gateway pattern con JWT filter**: el gateway de Spring Boot valida tokens y enruta peticiones REST al servicio correcto.
- **Auth Service desacoplado**: la emisión y verificación de tokens está aislada del resto de la lógica de negocio.
- **Hook de estado** (`useWebSocketRoom`): encapsula todo el ciclo de vida del WebSocket en un hook React reutilizable.
- **Geometría compartida**: `buildHexGeometry` exportada para reutilización sin duplicar código.

=== Conceptos de Desarrollo

- TypeScript estricto en el frontend con tipos compartidos entre componentes.
- Tests unitarios con Vitest + Testing Library (frontend) y Vitest + Supertest (users service).
- Tests de integración y benchmarks en Rust (`cargo test`, `cargo bench`).
- Tests E2E con Playwright + Cucumber (BDD). Las APIs externas se mockean con `page.route()` y `page.addInitScript()` (WebSocket falso inyectado en el navegador). Los escenarios cubren: registro, login, partida vs bot, lobby multijugador, flujo WebSocket completo (crear sala, unirse, movimientos, chat, errores), leaderboard y perfil.
- Cobertura de código reportada a SonarCloud y visible mediante badge en el README.

=== Conceptos Operativos

- Docker Compose como orquestador en desarrollo y producción.
- Variables de entorno para configurar URLs entre servicios y secretos (JWT_SECRET, DB_PASS) sin hardcodear valores.
- Prometheus + Grafana para monitorización de métricas del Users Service.
- Logs locales por servicio; integrables con sistemas centralizados en el futuro.
- El timeout del proxy WebSocket en Nginx se configura a 3600s para mantener partidas largas activas.
- CI/CD con GitHub Actions: en cada push se ejecutan tests y se publica la imagen Docker en GHCR.
